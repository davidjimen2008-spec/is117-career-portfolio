# Research method, AI use, and limitations

**Research question:** How do a frontend engineering internship and a junior frontend engineering role differ in responsibilities, qualifications, and portfolio evidence?

**Audience:** Students exploring frontend careers and reviewers evaluating the source-to-decision reasoning.

## Method

1. Select one internship and one junior role in the New York area.
2. Record employer-controlled job descriptions and a research observation date (November 12, 2026).
3. Extract the listed technologies, responsibilities, and qualifications into [role cards](./roles).
4. Compare the two roles and separate employer wording from the researcher's interpretation in the [comparison](./comparison).
5. Compare possible portfolio directions and select a staged plan, then define observable acceptance criteria in the [portfolio roadmap](../portfolio/plan).
6. Use GitHub issues, branches, and pull requests to make revisions inspectable. Request real reviewer feedback and a retest before claiming the peer-review cycle is complete.

## What AI helped with

AI assistance was used to help organize the research structure, draft and revise explanatory documentation, propose comparison tables and testing criteria, and implement and style the VitePress site and GitHub workflow. AI-generated text and code should not be mistaken for independent evidence or for work completed without assistance.

## What was actually established

- The repository contains dated notes and original employer URLs for two researched positions.
- The comparison and portfolio plan show proposed features and checks, not a completed React application.
- Issues #1–#4 and PRs #5–#9 record documentation and site revisions.
- GitHub Actions deployment success verifies the deployment workflow completed; it does **not** by itself establish that every public page or browser feature works.
- The peer-review log distinguishes owner-posted verification notes from an independent classmate retest.

## Limitations and next checks

The Priceline posting has not been independently reconfirmed in the recorded review; job availability can change. The redesigned site needs a documented live-browser check. React and API implementation tests remain unrun. Independent classmate feedback and retest should be recorded using real comments and observations, without inventing outcomes.

## What a reviewer can challenge

Open an original employer posting, check a specific requirement, compare it with the interpretation and proposed feature, then inspect the planned test. If the source differs from the recorded notes, update the evidence and explain whether the decision changes. See the [review log](../review/log).
